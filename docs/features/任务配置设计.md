# 任务配置设计

## 文档说明

本文档描述任务配置向导的完整交互流程和数据结构设计。

**文档版本**: v4.0
**最后更新**: 2026-07

---

## 交互流程

```
步骤1: 选择数据源
  ├── 选择源数据源（下拉列表）
  └── 选择目标数据源（支持多目标）

步骤2: 选择表
  ├── 左侧：源库表列表（checkbox）
  └── 右侧：已选表列表（可配置目标表名、字段选择）

步骤3: 同步配置
  ├── 同步模式：full / incremental
  ├── 批次大小：自适应 / 自定义
  ├── 并发数：默认 4
  └── 队列类型：memory / redis

步骤4: 确认配置
  ├── 配置预览
  └── 创建任务
```

---

## 双列表同步规则

- 左侧 checkbox 勾选 → 表添加到右侧
- 右侧 × 按钮移除 → 左侧 checkbox 自动取消勾选
- 左右状态严格同步

## 数据结构

### TaskConfig

```go
type TaskConfig struct {
    TargetIDs []string         `json:"TargetIDs"`
    Mappings  []DatabaseMapping `json:"Mappings"`
}

type DatabaseMapping struct {
    SourceDatabase string        `json:"source_database"`
    TargetDatabase string        `json:"target_database"`
    Tables         []TableConfig `json:"tables"`
}

type TableConfig struct {
    SourceTable string   `json:"source_table"`
    TargetTable string   `json:"target_table"`
    Fields      []string `json:"fields"`       // 空=全部字段
    BatchSize   int      `json:"batch_size"`   // 0=自适应
}
```

# 任务配置 — 完整设计文档

## 📋 文档说明

本文档详细描述 DataTrace 系统任务配置向导的交互流程、业务逻辑和数据结构设计。

**文档版本**: v3.0
**最后更新**: 2026-07-01
**技术栈**: Go + Gin + GORM + Vue 3 + Element Plus
**适用范围**: MySQL → MySQL 同步（1对1）

---

## 🎯 概述

任务配置模块采用**4步向导式**交互，引导用户完成从数据源选择到配置确认的完整流程。

### 核心流程

```
步骤一：数据源配置
   ├─ 左侧选择源数据源
   ├─ 右侧选择目标数据源（源和目标不能相同）
   └─ 支持快速创建数据源
   ↓
步骤二：库表配置
   ├─ 查询源库库表（两步加载：先库后表，树形结构）
   ├─ 支持修改库名（单个 + 批量）
   ├─ 支持修改表名（单个 + 批量）
   ├─ 支持部分字段同步
   └─ 显示重命名信息（当前名 + 原名）
   ↓
步骤三：同步配置
   ├─ 同步逻辑：全量 / 增量
   ├─ 初始化逻辑：DROP / TRUNCATE / DELETE
   └─ 遇错处理：停止 / 跳过
   ↓
步骤四：配置确认
   ├─ 源/目标库名称展示
   ├─ 同步库和表数量展示（点击查看详情）
   └─ 同步配置摘要
   ↓
保存任务配置
```

---

## 📝 步骤详解

### 步骤一：数据源配置

#### 交互模型

采用**左右布局**（源 ↔ 目标 双列选择器）：

```
┌──────────────────┐                      ┌──────────────────┐
│  选择源数据源      │                      │  选择目标数据源    │
│                  │                      │                  │
│  ○ 数据源A (MySQL)│    ──────────→      │  ● 数据源B (MySQL)│
│  ○ 数据源C (MySQL)│    单向选择          │                  │
│                  │                      │                  │
│  [+ 新建数据源]   │                      │  [+ 新建数据源]   │
└──────────────────┘                      └──────────────────┘
```

#### 功能要求

| 功能 | 说明 |
|------|------|
| 左右布局选择 | 左侧列出所有源类型匹配的数据源，右侧列出所有目标类型匹配的数据源 |
| 1对1限制 | 当前版本只支持选择 **1个源 + 1个目标** |
| 自我同步禁止 | 源数据源选择后，目标侧自动过滤该数据源，避免自己同步自己 |
| 快速创建 | 如果列表为空或无合适数据源，提供「+ 新建数据源」快捷入口 |
| 类型匹配 | 源和目标的数据源类型必须匹配（当前仅 MySQL→MySQL） |

#### 验证规则

- 源数据源**必选**（未选中时不可进入下一步）
- 目标数据源**必选**
- 源和目标**不能是同一个数据源实例**
- 源和目标的数据源类型必须一致

#### 数据结构

选中结果存储在任务配置中：

```json
{
  "source_id": "uuid-of-source-datasource",
  "target_id": "uuid-of-target-datasource"
}
```

### 步骤二：库表配置

这是整个任务配置中最核心、最复杂的步骤。采用**左右穿梭框**（Transfer/Shuttle）模式，左侧展示源库的库表结构，右侧展示已选中的库表及映射关系。

#### 2.1 整体布局

```
┌──────────────────────────────────┬──────────────────────────────────┐
│  源库结构（只读）                 │  目标映射（可编辑）               │
│                                  │                                  │
│  □ 数据库A                        │  □ 数据库A（原名：Aceshi）       │
│    ├─ □ 表1              [字段]   │    ├─ 表1  [字段]  [原名:t1]  × │
│    ├─ □ 表2              [字段]   │    ├─ 表2  [字段]  [原名:t2]  × │
│    └─ □ 表3              [字段]   │    └─ 表3  [字段]  [原名:t3]  × │
│                                  │               🗑️               │
│  □ 数据库B                        │                                  │
│    └─ □ 表4              [字段]   │  ┌──────────────────────────┐   │
│                                  │  │  批量修改 ▼              │   │
│         已选: 3个库, 10张表       │  └──────────────────────────┘   │
│                                  │                                  │
│    [▶ 展开]  [添加 →]  [← 移除]   │                                  │
└──────────────────────────────────┴──────────────────────────────────┘
```

#### 2.2 树形结构 + 两步加载

**设计目标**：减少后端压力，避免一次性查询所有库表导致的性能问题。

**加载流程**：

```
步骤 1: 用户进入步骤二，前端调用 GET /api/v1/datasources/{id}/databases
         └─ 返回源库的数据库列表
         └─ 左侧树只显示库名，不展开

步骤 2: 用户点击展开某个数据库（▶ 箭头）
         └─ 调用 GET /api/v1/datasources/{id}/tables/{database}
         └─ 返回该库下的所有表名
         └─ 左侧树展开显示该库下的表

步骤 3: 用户勾选表，点击「添加 →」将表移到右侧
```

**核心规则**：
- 进入步骤二时**只查询库名列表**
- **懒加载**：点击展开时才加载该库下的表
- 如果某库已被选中（在右侧），再次展开时不再请求（从本地缓存读取）
- 提供「全部展开 / 全部折叠」快捷操作

#### 2.3 库名修改

支持两种模式：**单库修改** 和 **批量修改**。

##### 单库修改

每个已选中到右侧的库名后面有一个 ✏️（铅笔）图标，点击弹出编辑框：

```
┌───────────────────────────────────────┐
│  修改目标库名                          │
│                                       │
│  源库名: test                          │
│  目标库名: [ceshi_______________]      │
│                                       │
│          [取消]     [确认修改]          │
└───────────────────────────────────────┘
```

- 修改后右侧库名实时更新为 `ceshi`
- 库名行追加显示 `（原名：test）` 提示
- 如果目标库名与源库名相同，不显示原名提示

##### 批量修改

点击「批量修改」按钮弹出批量修改对话框：

```
┌───────────────────────────────────────────────┐
│  批量修改库名                                   │
│                                               │
│  ○ 前缀添加       [prefix_]       共 3 个库    │
│  ○ 后缀添加       [_suffix]       共 3 个库    │
│  ○ 匹配替换       [test_] → [prod_] 共 3 个库  │
│                                               │
│  预览：                                        │
│  test     → test_prefix                        │
│  dev      → dev_prefix                         │
│  staging  → staging_prefix                     │
│                                               │
│          [取消]     [确认修改]                   │
└───────────────────────────────────────────────┘
```

**三种模式**：

| 模式 | 输入 | 示例 | 效果 |
|------|------|------|------|
| 前缀添加 | 输入前缀字符串 | `prod_` | `test` → `prod_test` |
| 后缀添加 | 输入后缀字符串 | `_backup` | `test` → `test_backup` |
| 匹配替换 | 输入「查找」和「替换」字符串 | `test_` → `prod_` | `test_db` → `prod_db` |

- 每次修改后实时在预览区域显示变更前后的库名
- 确认后将所有变更应用到当前已选中的库
- 预览区域显示：原名 → 修改后名

#### 2.4 表名修改

逻辑与库名修改**完全一致**，但作用域为单个数据库下的表。

##### 单表修改

每个已选中到右侧的表名后面有一个 ✏️ 图标，点击弹出编辑框（同库名编辑交互）。

##### 批量修改（表级）

点击「批量修改」按钮后，可选择作用范围：

```
┌───────────────────────────────────────────────┐
│  批量修改表名         作用范围: [当前库 ▼]     │
│                                               │
│  ○ 前缀添加       [t_]             共 3 张表   │
│  ○ 后缀添加       [_bak]           共 3 张表   │
│  ○ 匹配替换       [old_] → [new_]  共 3 张表   │
│                                               │
│  预览：                                        │
│  users    → t_users                            │
│  orders   → t_orders                           │
│  products → t_products                         │
│                                               │
│          [取消]     [确认修改]                   │
└───────────────────────────────────────────────┘
```

**作用范围选项**：
- 当前库：只修改当前选中数据库下的所有表
- 所有库：修改所有已选中数据库下的所有表

#### 2.5 部分字段同步

每张表（左侧和右侧）都有一个「字段」按钮，点击后弹出字段选择对话框：

```
┌────────────────────────────────────┐
│  选择字段 — users                  │
│                                    │
│  ☑ 全选                            │
│  ─────────────────────────         │
│  ☑ id                              │
│  ☑ name              ← 已选 3/8    │
│  ☑ email                          │
│  ☐ age                            │
│  ☐ phone                          │
│  ☐ address                        │
│  ☐ created_at                     │
│  ☐ updated_at                     │
│                                    │
│          [取消]     [确认]          │
└────────────────────────────────────┘
```

**规则**：
- 点击「字段」按钮后，调用 `GET /api/v1/datasources/{id}/columns?database={db}&table={table}` 获取字段列表
- 默认**全选**所有字段
- 取消全选后至少保留一个字段（不允许零字段）
- 选择后按钮上显示已选字段数，如 `字段(3)`
- 如果不做任何选择，默认为同步所有字段

#### 2.6 重命名显示规则

右侧列表中的库/表名显示规则：

| 情况 | 显示格式 | 示例 |
|------|---------|------|
| 未修改 | 直接显示原名 | `users` |
| 已修改 | 目标名（原名：源名） | `t_users（原名：users）` |
| 批量修改后 | 同上 | `t_users（原名：users）` |

#### 2.7 全选/取消全选逻辑

| 操作 | 效果 |
|------|------|
| 选中源侧库 checkbox | 勾选该库下所有表（标记为待添加） |
| 取消选中源侧库 checkbox | 取消该库下所有表的待添加标记 |
| 全选某库的全部表 | 自动勾选该库的 checkbox |
| 取消某库的部分表 | 库 checkbox 变为半选状态（indeterminate） |

#### 2.8 右侧已选项操作

| 操作 | 效果 |
|------|------|
| 勾选右侧表 → 点击「移除」 | 所有勾选的表从右侧消失，左侧对应取消勾选 |
| 点击右侧表行的 × | 该表从右侧消失，左侧取消勾选 |
| 点击右侧库行的 🗑️ | 该库下所有表从右侧消失，左侧对应库表全部取消勾选 |
| 点击库名/▶箭头 | 展开/折叠该库下的表列表（独立于左侧） |

#### 2.9 分步加载 API

```http
# 第一步：获取源库数据库列表
GET /api/v1/datasources/{sourceId}/databases
Response:
{
  "code": 200,
  "data": ["test", "cmdb", "cicd", "datatrace"]
}

# 第二步：获取指定数据库下的表列表
GET /api/v1/datasources/{sourceId}/tables/{database}
Response:
{
  "code": 200,
  "data": ["users", "orders", "products"]
}

# 第三步：获取表的字段列表（用于字段选择）
GET /api/v1/datasources/{sourceId}/columns?database={db}&table={table}
Response:
{
  "code": 200,
  "data": ["id", "name", "email", "age", "phone", "address", "created_at", "updated_at"]
}
```

### 步骤三：同步配置

> 此步骤在步骤一的右侧和步骤二之后，配置同步执行的相关参数。

#### 3.1 配置项一览

| 配置项 | 选项 | 默认值 | 说明 |
|--------|------|--------|------|
| **同步逻辑** | 全量 / 增量 | 全量 | 全量：一次性同步所有数据；增量：Binlog 实时同步变更 |
| **初始化逻辑** | DROP / TRUNCATE / DELETE | DROP | 目标表已存在时的处理策略 |
| **遇错处理** | 停止 / 跳过 | 跳过 | 同步过程中遇到错误时的应对策略 |

#### 3.2 同步逻辑详解

| 同步模式 | 说明 | 适用场景 |
|---------|------|---------|
| **全量同步** | 一次性将源库数据全部同步到目标库 | 首次迁移、一次性数据拷贝 |
| **增量同步** | 基于 Binlog 监听源库变更，实时应用到目标库 | 持续数据同步、灾备 |

**当选择增量同步时，隐含固定执行「先全量 + 后增量」流程**：
1. 先执行全量同步（将源库已有数据同步到目标）
2. 全量完成后自动进入增量监听模式
3. 实时同步源库后续的数据变更

#### 3.3 初始化逻辑详解

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **DROP** | 删除目标库已存在的同名表，重新创建并同步 | 完全覆盖，确保结构与源一致 |
| **TRUNCATE** | 保留表结构，清空所有数据，重新同步 | 仅需更新数据，表结构不变 |
| **DELETE** | 不删除表也不清空，直接插入/覆盖数据 | 目标表已有部分数据，增量补充 |

#### 3.4 遇错处理详解

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **跳过** | 记录错误日志，标记当前表为失败，继续同步其他表 | 非关键业务，容忍部分表失败 |
| **停止** | 记录错误日志，立即停止所有同步工作 | 关键数据，必须保证完整性和一致性 |

#### 3.5 配置数据结构

```json
{
  "sync_config": {
    "sync_mode": "full",
    "init_strategy": "drop",
    "error_strategy": "skip",
    "batch_size": 2500,
    "workers": 4
  }
}
```

#### 4.3 保存逻辑

```
1. 验证任务名称
   ├─ 必填
   └─ 2-50 个字符，不能重复
   ↓
2. 构建完整任务配置 JSON
   ├─ 数据源 ID（source_id / target_id）
   ├─ 库表映射（database_mappings）
   └─ 同步参数（sync_config）
   ↓
3. 保存到 sync_tasks 表
   ├─ 生成任务 ID（UUID）
   ├─ 状态设为 configured
   └─ config 字段存储完整 JSON
   ↓
4. 生成任务单元配置（task_unit_configs）
   └─ 每个表生成一条记录
   ↓
5. 显示成功提示
   ↓
6. 跳转到任务监控页
```

## 📊 完整配置数据结构

### 任务配置 JSON（存储在 sync_tasks.config 字段）

```json
{
  "source_id": "uuid-of-source-datasource",
  "target_id": "uuid-of-target-datasource",
  "database_mappings": [
    {
      "source_db": "test",
```

## 🔄 编辑任务

### 编辑流程

```
用户点击「编辑任务」
   ↓
加载任务配置（GET /api/v1/tasks/:id）
   ↓
解析 config JSON，回填到各步骤
   ↓
进入向导编辑器（可跳转到任意步骤）
   ↓
用户修改配置（任意步骤）
   ↓
保存更新
   ├─ 更新 sync_tasks 表
   ├─ 删除旧的 task_unit_configs
   └─ 生成新的 task_unit_configs
```

### 限制条件

- 如果任务**正在运行**，必须先停止才能编辑
- 编辑后原有运行记录（task_unit_runtimes）将被清除
- 编辑后任务状态重置为 `configured`，需要重新启动

## 🔧 实现建议

### 分步加载性能

- 后端缓存数据库列表（TTL 30秒），避免频繁查询 information_schema
- 表列表可按需懒加载，首次仅返回库名列表
- 字段列表不做缓存，因为表结构变更不频繁

### 批量修改的前端实现

- 批量操作是纯前端计算，不需要后端接口
- 用户点击确认后，将计算结果写入本地的 `database_mappings` 数据
- 最终保存时一次性提交完整配置 JSON

### 字段选择的存储优化

- 如果用户没有主动点击字段按钮修改，`columns` 字段设为 `null`
- 后端读取时：`null` 表示同步所有字段，非 `null` 数组表示只同步指定字段
- 这样避免在默认场景下存储冗余数据
